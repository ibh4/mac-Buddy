# 官方营养资料（list-nutrition-foods）· 取数、解析与匹配

> 本文件记录「这一餐的能量卡」背后的真实数据来源、解析坑点与匹配策略。
> 数据来自麦当劳官方 MCP 工具 `list-nutrition-foods`，按「每份（件）」计量。
> 下方表格为 **2026-10-10 真实抓取快照**，仅作参考；运行时仍以实时拉取为准。

## 1. 怎么取数（关键坑点）

- 工具 **`list-nutrition-foods` 无入参**。
- **真实返回是被「描述性文本」包裹的 JSON**：外层是 markdown 说明（`# API Response Information` … `## Original Response`），里面才是
  `{ success, code, message, datetime, traceId, data }`，其中 `data` 才是真正的纯文本营养表。
- ⚠️ **不要直接走纯文本通道取整个响应**：那样会拿到 6000+ 字的 markdown 外壳，`parseNutritionTable` 解析不出任何行 → 能量卡全空（「暂无数据」/ 0/N 匹配）。
- ✅ 正确做法：走**结构化通道**取 `data` 字段（内层字符串），再按表头解析。本项目 `service.getNutritionFoods()` 已改为 `callMcpTool(...).data`。
- 表头格式：`[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:`，随后每行 `中薯条,null,1210,289,4,12,38,165,18`（`null` 表示该项无数据）。
- 真实模式拉取后缓存 6 小时（`nutrition.ts` 的 TTL）；演示模式用 `DEMO_NUTRITION`（虚构，界面标注「演示数据」）。

## 2. 匹配策略（nutrition.ts）

餐品（菜单名 / 历史订单名）要对应到营养表里的「商品名」。两者命名常不一致，采用以下规则，**只做确定性对齐，绝不臆测份量、绝不编造数据**：

1. `normalizeName`：去括号/空格/连字符噪声；剥尾部计量词（杯/盒装/罐/瓶/份/个/块/包/只/根/片）与套餐标记（组合/套餐/超值/精选/随心配/风味/常规）。
2. `nameCandidates`：对两类系统性错位生成等价候选键，**只换位置、不去份量**（避免大/中/小薯条混为同一份）：
   - **规格位置互换**：表用「大薯条」、菜单用「薯条（大）」→ 互相生成对方；
   - **堡/汉堡归一**：「麦辣鸡腿堡」↔「麦辣鸡腿汉堡」互认。
3. `computeMealNutrition`：
   - **套餐**只累计 `comboItemList` 的组成项，不重复计入套餐本身；组成项无数据时如实标「暂无数据」；
   - **数量**按 `quantity` 累加；缺失项不计入合计（不是 0），并记入 `missingNames`；
   - 能量优先 kcal，仅 kJ 时按 `1 kcal = 4.184 kJ` 换算；
   - 部分匹配显示覆盖情况（如「4 项中 3 项已匹配」）；**糖恒为「暂无数据」**（官方表未提供，绝不由碳水推算；碳水不是糖，钠不是盐）。

### 已知无法匹配的诚实情形（不是 bug）

- **缺规格的单品**：如菜单只写「玉米杯」（无大/小）、「美式咖啡」（官方实际是「鲜萃咖啡/美式」系列按杯型列），无法确定份量 → 不强行匹配，标「暂无数据」。
- **官方表未收录的单品**：如「吉士蛋麦满分」官方营养表没有（只有猪柳/烟肉/火腿扒/板烧麦满分等），其套餐「吉士蛋麦满分组合」的组成项若含它即如实标「暂无数据」。
- **促销/组合编码**：`99` 开头编码本身不在营养表，必须靠 `comboItemList` 展开；若历史订单未带组成项则整体无法匹配。

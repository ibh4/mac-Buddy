# 架构说明

## 一句话

**Mac-Buddy · 麦麦搭子**（参赛名称：Mac-Buddy 麦麦搭子——懂你口味的点餐助手）= 一个本地后端（唯一持有 MCP Token）+ 一个纯前端单页应用 + 一组确定性纯函数。

后端负责所有真实接口调用与本地持久化；前端只做展示与交互，永远拿不到 Token。

```
浏览器（前端 SPA）
   │  /api/*（仅本地 127.0.0.1）
   ▼
本地后端（Express + better-sqlite3）
   │  Streamable HTTP + Authorization: Bearer <token>
   ▼
麦当劳 MCP（https://mcp.mcd.cn）
```

## 目录职责

| 目录 | 职责 |
| --- | --- |
| `apps/server` | 后端：MCP 客户端、路由、本地数据库、全部业务纯函数 |
| `apps/web` | 前端：React + Vite 单页应用，构建产物由后端托管 |
| `skills/mcd-buddy` | WorkBuddy / MCP 客户端可直接安装的 Skill（含 references、scripts） |
| `tests` | 离线单元测试（vitest），全部在演示模式下运行 |
| `examples` | 虚构示例数据（不参与运行） |
| `docs` | 交付文档：架构、演示模式、参赛说明、截图 |
| `scripts` | 本地启动、自检、发布前校验脚本 |

> `packages/core` 未建立：当前前后端没有真正共享的代码（类型在两侧各自定义），
> 为了目录好看而抽一个空包反而增加维护成本。若将来出现共享逻辑再抽。

## 分层原则

后端内部严格分三层，这是整个项目最重要的设计约束：

1. **纯函数层**（`apps/server/src/` 下的 `catalog.ts` / `constraints.ts` / `tweak.ts` /
   `randomPicker.ts` / `foodSign.ts` / `footprint.ts` / `nutrition.ts` / `lighter.ts` / `coupons.ts`）
   - 不调用 MCP、不读环境变量、不碰数据库；
   - 所有输入通过参数注入，**因此可以在完全离线的情况下被单元测试覆盖**；
   - 随机结果由 `mulberry32(hashString(seed))` 决定，同一天同一种子一定得到同一结果。

2. **编排层**（`generators.ts`）
   - 唯一把真实 MCP 数据组装进纯函数的地方；
   - 负责菜单缓存（5 分钟）、营养表缓存（6 小时）、食签当日缓存；
   - 演示/真实模式在这里分流（演示数据不冒充真实订单，用 `isDemo` 标记到底）。

3. **I/O 层**（`service.ts` / `mcpClient.ts` / `routes.ts` / `db.ts`）
   - MCP 调用、SQLite 读写、HTTP 路由；
   - Token 只存在于这一层。

## 数据流：一次「微调」发生了什么

```
用户点「今天微微调」
  → generators.runTweak()
      ├─ buildCatalog()        ← MCP query-meals（5 分钟缓存）
      ├─ buildDetailProvider() ← MCP query-meal-detail（仅对餐单里已有的套餐）
      ├─ checkAvailability()   ← 判断当前门店是否可售
      └─ generateTweakPlans()  ← 纯函数：枚举同品类替换 + 套餐侧项替换
                                  逐条过 validatePlan（锁定/预算/可见/可售/处数）
                                  冲突时不突破约束，只返回原因与“可放宽哪一项”
  → 前端展示方案卡
  → 用户点「另存一版」才写入版本表
```

## 营养口径（能量卡）

营养模块是本项目中约束最严的一块，任何一条都不允许被"顺手方便"地打破：

- 只在**规格与计量基准可核对**时匹配；名称相似但份量未知的不认定为同一份量；
- 官方营养表按「每份」给出且无重量列，因此**只按数量累加，不做每 100g 换算**；
- 能量优先取 kcal；只有 kJ 时按 `1 kcal = 4.184 kJ` 换算；
- 套餐只累计其组成项，**不重复计入套餐本身**；
- 特制（如去酱）无对应数据时标注「特制后的营养变化未知」，**绝不编造减少值**；
- 缺失数据一律为 `undefined`，界面显示「暂无数据」，**绝不填 0**；
- 部分匹配时给出覆盖情况（如「4 项中 3 项已匹配」），不把部分合计写成整餐总量；
- 碳水不是糖，钠不是盐；糖在官方表中无数据，恒为「暂无数据」，**绝不由碳水推算**；
- 用当前营养资料分析历史餐单时，必须标明资料口径，**不声称还原历史摄入**。

## 为什么"确定性"这么重要

用户改餐的依据必须可复现、可解释：

- 同一天、同一种子 → 同一份食签（缓存到当日 24:00）；
- 同一餐单 + 同一约束 → 同一组微调方案；
- 所有营养差值、价格差值由代码计算，语言模型只负责把结果说成人话。

这既是为了可测试，也是为了**不把用户的钱和饭交给一个不可复现的过程**。

## 安全边界

- Token 只在 `apps/server/.env`（已被 `.gitignore` 忽略），后端自动补 `Bearer ` 前缀；
- 后端只监听 `127.0.0.1`，并对写操作做来源校验；
- 前端构建产物与日志中不含 Token（发布前脚本会校验）；
- 演示模式与真实模式严格区分，演示数据不冒充真实订单；
- 演示模式不产生任何真实订单或支付链接；真实模式下也只有用户点「确认下单」才会调用 `create-order`。
